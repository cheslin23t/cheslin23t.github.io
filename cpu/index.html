01 / THE BIG PICTURE

Small words.
Real computation.

Instructions live in ROM. A program counter selects an address. The instruction describes what to load or calculate, and which register receives the result.

You’re looking at the actual exported Minecraft build. Scroll to inspect one region at a time, or use the labeled chapter links. Switch to whole-build context to locate each region in the machine. The model preserves the schematic’s block positions; it does not simulate redstone.

The instruction’s path

  1. AddressThe six-bit PC selects one of 64 ROM words.
  2. DecodeThe 16-bit word supplies an operation and register selections.
  3. Read & calculateTwo operand paths feed the eight-bit ALU.
  4. StoreThe selected destination retains the result for a later instruction.

This is the functional data flow. It is not a claim about four clock phases or a traced route through every wire.

02 / KEEPING TIME

One address.
Every 7.3 seconds.

The repaired native clock advances once every 146 game ticks. At 20 TPS, that is 7.3 seconds per instruction address.

000000 → 000001

The six-bit PC visits 64 addresses, then wraps to zero. The six highlighted repeaters are confirmed PC state landmarks. The camera frames the approximate PC region; connected control circuitry extends beyond it. The PC reset is synchronous: assert reset, allow it to settle, then clock the counter. This was tested; it does not clear the register banks.

Why slow the clock?

Redstone signals take time to propagate. A correct Boolean result is not enough: it must arrive before the storage circuit locks it in. The repaired feedback loop gives the machine more settling time.

Original period44 ticksRepaired period146 ticks

Ten consecutive native PC advances measured 146 ticks each. The close-up marks the six PC state bits; the clock loop and reset controls extend beyond this crop.

03 / PROGRAM STORAGE

A program.
With room to breathe.

The ROM holds 64 × 16-bit words. The safe layout starts with NOP at address 0, puts instructions at 1, 3, 5…53, and leaves a NOP after each.

00 0000 NOP01 A58B LDI R1, 16502 0000 NOP03 3C4B LDI R2, 60

The highlight follows the exact programming-cell coordinates; air cells stay invisible. That leaves capacity for 27 logical instructions. Addresses 56–63 stay NOP: address 60 fetches 56, and 61 fetches 57.

How blocks encode a word

Each address has 16 programming positions. A west-facing redstone wall torch encodes 1; air encodes 0. The address decoder selects the word, and the bit lanes carry its pattern onward.

The physical scene shows the original saved ROM. The listing above and the addition replay below use a separate example program.

Measured limit: unique-word fetch testing passed 62 of 64 addresses. Keeping the aliased tail empty avoids executing unintended instructions.

04 / THE INSTRUCTION

Sixteen bits.
Every field matters.

The camera moves to the operation-label signs in the physical build. For register operations, each register’s four-bit number is reversed independently. The whole instruction is never reversed.

4A / lhs
8B / rhs
Cdest
1ADD

48C1 means ADD R3, R2, R1: R2’s 0010 becomes 0100, R1’s 0001 becomes 1000, and R3’s 0011 becomes 1100.

LDI uses the top eight bits for its immediate value, without reversal. INC reads its source on physical B with physical A set to R0.

Decode means controlling the hardware

The opcode selects control signals, including ALU inversion/carry controls and read/write enables. The register fields select the sources and destination. LDI instead carries a literal byte to store.

For example, A58B splits into immediate A5 (165), reversed destination 8 (R1), and opcode B (LDI).

A real decode repair: AND was missing its invert-A torch, and its enable buses did not receive the intended signal. Restoring both made the tested AND cases pass.

05 / WORKING VALUES

Eight bits.
A value that stays.

R1–R14 hold unsigned values from 0 to 255. R0 reads as zero in tested operand operations; writes do not persist.

R1 ← 10100101 165

The two banks contain 15 × 8 × 2 = 240 storage repeaters. They hold mirrored copies of the register values, rather than 30 independent registers. The highlighted positions include the physically present R15. The camera bounds are approximate; highlighting R15 does not imply it works correctly. R15 retains loaded data, but both operand reads return zero; the compiler excludes it.

A locked repeater is a one-bit memory

A repeater normally follows its rear input after a delay. A powered repeater or comparator pointing into its side can lock it. While locked, its output stays at the previous state even if the input changes.

  1. AcceptThe write controls allow the selected storage cells to take new data.
  2. HoldThe lock preserves each bit for use by later instructions.

In these storage probes, the electrical state is inverted: powered = logical 0; unpowered = logical 1. Eight stored bits make a byte. The browser’s cyan overlay identifies cells; it does not show their value.

06 / DOING THE WORK

From two values
to one result.

The ALU takes two eight-bit operands and produces an eight-bit result. The opcode controls which arithmetic or logic operation it performs. The eight cyan repeaters mark its measured outputs. Arithmetic wraps modulo 256: 255 + 1 = 0.

60 + 165 = 225

Physical A is lhs; physical B is rhs. So SUB R3, R2, R1 computes R2 − R1.

Supported: NOP · ADD · SUB · AND · NAND · OR · XOR · NOR · XNOR · INC · LDI

Eight parallel result bits

The highlighted repeaters are isolated ALU outputs, one per bit. Bit 0 contributes 1, bit 1 contributes 2, and bit 7 contributes 128. Reading them together gives the unsigned result.

00111100 60 · physical A10100101 165 · physical B11100001 225 · result

The nearby dust staircase combines the output for zero detection. It is not eight independent result wires, so it cannot be read like the isolated output repeaters.

A native-clock mixed program passed ADD, SUB, AND, NAND, OR, XOR, NOR, XNOR and INC with operands 165 and 60. This is measured evidence, not an exhaustive truth-table proof.

Addresses 56–63 are reserved NOP. At PC 60 the CPU fetches 56; at PC 61 it fetches 57. Playback continues through padding and wraps. Pause is a viewer control, not a hardware HALT.

Built in blocks.
Bound by the hardware.

The clock keeps going.

There is no verified HALT. After address 63, the PC wraps and repeats. The operator must stop the clock externally.

Some behavior stays unknown.

Conditional branches, overflow semantics, a full-machine reset, internal microsteps, RAM, stack, CALL/RET and I/O are not verified. The PC-only synchronous reset and zero detector have been tested. DEC is faulty. R15 operand reads fail.

Conservative by design.

The compiler inserts NOP gaps and rejects destination/source overlap. Those sequences are not fully certified; this is a compiler policy, not proof they all fail physically.
