01 / THE BIG PICTURE

Small words.
Real computation.

Instructions live in ROM. A program counter selects an address. The instruction describes what to load or calculate, and which register receives the result.

You’re looking at the actual exported Minecraft build. Scroll to move through it: selected blocks turn cyan while the rest of the machine fades back. The model preserves the schematic’s block positions; it does not simulate redstone.

02 / KEEPING TIME

One address.
Every 7.3 seconds.

The repaired native clock advances once every 146 game ticks. At 20 TPS, that is 7.3 seconds per instruction address.

000000 → 000001

The six-bit PC visits 64 addresses, then wraps to zero. The six highlighted repeaters are confirmed PC state landmarks. The camera frames the approximate PC region; connected control circuitry extends beyond it. Starting at PC 0 is an illustrative assumption; reset behavior is unknown.

03 / PROGRAM STORAGE

A program.
With room to breathe.

The ROM holds 64 × 16-bit words. The safe layout starts with NOP at address 0, puts instructions at 1, 3, 5…53, and leaves a NOP after each.

00 0000 NOP01 A58B LDI R1, 16502 0000 NOP03 3C4B LDI R2, 60

The highlight follows the exact programming-cell coordinates; air cells stay invisible. That leaves capacity for 27 logical instructions. Addresses 56–63 stay NOP: address 60 fetches 56, and 61 fetches 57.

04 / THE INSTRUCTION

Sixteen bits.
Every field matters.

The camera moves to the operation-label signs in the physical build. For register operations, each register’s four-bit number is reversed independently. The whole instruction is never reversed.

4A / lhs
8B / rhs
Cdest
1ADD

48C1 means ADD R3, R2, R1: R2’s 0010 becomes 0100, R1’s 0001 becomes 1000, and R3’s 0011 becomes 1100.

LDI uses the top eight bits for its immediate value, without reversal. INC reads its source on physical B with physical A set to R0.

05 / WORKING VALUES

Eight bits.
Fourteen usable registers.

R1–R14 hold unsigned values from 0 to 255. R0 reads as zero in tested operand operations; writes do not persist.

R1 ← 10100101 165

R15 can retain loaded data, but its operand reads fail. The compiler excludes it. The model highlights 240 confirmed storage repeaters across the two mirrored banks, including the physically present R15. The camera bounds are approximate; highlighting R15 does not imply it works correctly.

A displayed register value here is explanatory state. There is no verified CPU output port; output(x) is a compiler declaration.

06 / DOING THE WORK

From two values
to one result.

The eight highlighted repeaters are confirmed ALU output landmarks. The camera frames the approximate ALU region without assigning every connected wire to it. ADD, SUB and the bitwise operations work on eight-bit operands. Arithmetic wraps modulo 256: 255 + 1 = 0.

60 + 165 = 225

Physical A is lhs; physical B is rhs. So SUB R3, R2, R1 computes R2 − R1.

Supported: NOP · ADD · SUB · AND · NAND · OR · XOR · NOR · XNOR · INC · LDI

Illustrative starting address. Register values are unknown.

Addresses 56–63 are reserved NOP. At PC 60 the CPU fetches 56; at PC 61 it fetches 57. Playback continues through padding and wraps. Pause is a viewer control, not a hardware HALT.

Built in blocks.
Bound by the hardware.

The clock keeps going.

There is no verified HALT. After address 63, the PC wraps and repeats. The operator must stop the clock externally.

Some behavior stays unknown.

Branches, reset, flags, internal microsteps, RAM, stack, CALL/RET and I/O are not verified. DEC is faulty. R15 operand reads fail.

Conservative by design.

The compiler inserts NOP gaps and rejects destination/source overlap. Those sequences are not fully certified; this is a compiler policy, not proof they all fail physically.
